## Scope and principles

This record covers the Phase 0 static roster, parent registration form, private registration store, any coordinator spreadsheet exported from that store, and the planned v1 data flows described below. Parents or guardians submit every child-related field. Students do not create accounts. Student names and faces do not appear on public pages.

The Phase 0 implementation does not collect a student last name, birthdate, school, payment information, account password, or public profile. The public pages use no third-party analytics or advertising trackers.

## Parent access, correction, export, and deletion

1. The parent emails `TODO(owner: monitored privacy mailbox; may match NEXT_PUBLIC_ABUSE_EMAIL)` from the address used on the request.
2. The privacy owner confirms the parent email and asks only for the minimum additional detail needed to locate the request.
3. The coordinator searches the private store by parent email. There is no public lookup tool.
4. Export uses a readable JSON or CSV copy of only that parent's matching records.
5. Correction replaces the inaccurate private record. Deletion removes the matching database row or JSONL record and every coordinator spreadsheet copy.

## Consent capture

The registration form requires the checkbox: "I am the parent/guardian and I consent to sending this lesson request." The server rejects the request when consent is absent. ## Breach procedure

1. Contain: revoke affected credentials, disable the registration action if needed, and preserve relevant Vercel, Neon, and access logs.
2. Assess: identify the records, people, fields, time range, and subprocessors affected. Determine whether a child-related field was exposed.
3. Escalate: notify `TODO(owner: incident lead)`, `TODO(owner: administrator contact)`, provider security contacts, and legal or privacy counsel.
4. Notify: follow the launch jurisdiction's required regulator, administrator, and parent timelines. Record the source for those timelines in `TODO(owner)`.
5. Remediate: rotate credentials, close the root cause, validate access controls, and document the change.
6. Record: keep an incident timeline, decisions, notification copies, and a post-incident review in `TODO(owner: restricted location)`.
